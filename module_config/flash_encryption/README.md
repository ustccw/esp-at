# ESP-AT Flash Encryption + NVS Encryption Configuration Guide (Development Mode)

This document describes how to enable **Flash Encryption** and **NVS Encryption** for the ESP-AT project. It uses `module_config/module_esp32c6_default/` as a reference example to demonstrate the specific modification steps. For other modules, adjust offsets and sizes according to your flash layout.

> **Note**: This guide only covers **Development Mode**. In Development Mode, the flash encryption key is generated by the chip on first boot and written to eFuse. The number of times encrypted data can be reflashed is limited.

---

## Overview

With Flash Encryption enabled, firmware and data partitions stored in flash are cryptographically protected. NVS Encryption further protects NVS-formatted partitions (such as `mfg_nvs`) using a separate key stored in the `nvs_key` partition.

**Key file**: `module_config/flash_encryption/sample_encryption_keys.bin`
This is a pre-generated NVS encryption key used at build time to encrypt `mfg_nvs.bin`, and flashed to the `nvs_key` partition for runtime access.

---

## Step-by-Step Modifications

The following example uses `module_config/module_esp32c6_default/` as a reference. For other modules, adjust offsets and sizes according to your flash layout.

### Step 1: Modify `partitions_at.csv`

Add a `Flags` column. Mark partitions that require Flash Encryption with `encrypted`. Add a new `nvs_key` partition (type: `data`, subtype: `nvs_keys`).

**Before** (original `module_esp32c6_default`):

```
# Name, Type, SubType, Offset, Size
otadata, data, ota, 0xd000, 0x2000
phy_init, data, phy, 0xf000, 0x1000
nvs, data, nvs, 0x10000, 0xE000
at_customize, 0x40, 0, 0x1E000, 0x42000
ota_0, app, ota_0, 0x60000, 0x1d0000
ota_1, app, ota_1, 0x230000, 0x1d0000
```

**After**:

```
# Name, Type, SubType, Offset, Size, Flags
otadata, data, ota, 0xf000, 0x2000,
phy_init, data, phy, 0x11000, 0x1000,
nvs, data, nvs, 0x12000, 0xE000,
at_customize, 0x40, 0, 0x20000, 0x3f000,
nvs_key, data, nvs_keys, 0x5f000, 0x1000, encrypted
ota_0, app, ota_0, 0x60000, 0x1d0000, encrypted
ota_1, app, ota_1, 0x230000, 0x1d0000, encrypted
```

Key changes:
- The partition table offset moves from `0x8000` to `0xA000` (the bootloader grows larger when Flash Encryption is enabled, so all partitions must shift forward).
- A new `nvs_key` partition (`data, nvs_keys`) is added and marked `encrypted` to store the NVS encryption key.
- `ota_0` and `ota_1` are marked `encrypted`.
- The `at_customize` offset changes from `0x1E000` to `0x20000`, and its size is reduced from `0x42000` to `0x3f000` (to make room for the `nvs_key` partition; the `at_customize` end address `0x5f000` is immediately followed by `nvs_key`).
- `at_customize` is **not** marked `encrypted`; the build system flashes it with `ALWAYS_PLAINTEXT`.

### Step 2: Modify `at_customize.csv`

Adjust the `mfg_nvs` offset to match the new partition layout, and reduce `fs_storage` to fit within the resized `at_customize` partition.

**Before**:

```
# Name, Type, SubType, Offset, Size
mfg_nvs, data, nvs, 0x1f000, 124K
fs_storage, data, 0xff, 0x47000, 100K
```

**After**:

```
# Name, Type, SubType, Offset, Size
mfg_nvs, data, nvs, 0x21000, 124K
fs_storage, data, 0xff, 0x47000, 70K
```

- The `mfg_nvs` offset changes from `0x1f000` to `0x21000` (= `at_customize` offset `0x20000` + `0x1000` reserved space).
- `fs_storage` is reduced from 100K to 70K to stay within the `at_customize` partition boundary (`0x47000` + 70K = `0x58800` < `0x5f000`).

### Step 3: Modify `sdkconfig.defaults`

Add the following configuration options.

**3.1 — Increase the partition table offset** (bootloader size increases):

```
CONFIG_PARTITION_TABLE_OFFSET=0xA000
```

**3.2 — Enable Flash Encryption (Development Mode) + NVS Encryption**:

```
# Flash encryption (development) + NVS encryption
CONFIG_SECURE_FLASH_ENC_ENABLED=y
CONFIG_SECURE_FLASH_ENCRYPTION_MODE_DEVELOPMENT=y
CONFIG_NVS_ENCRYPTION=y
CONFIG_SECURE_FLASH_UART_BOOTLOADER_ALLOW_ENC=y
CONFIG_SECURE_FLASH_UART_BOOTLOADER_ALLOW_DEC=y
CONFIG_SECURE_FLASH_UART_BOOTLOADER_ALLOW_CACHE=y
```

**3.3 — Update the AT custom partition table offset** (must match the `at_customize` offset in `partitions_at.csv`):

```
CONFIG_AT_CUSTOMIZED_PARTITION_TABLE_OFFSET=0x20000
```

## Build

```bash
./build.py build
```

The build system will automatically:
1. When `CONFIG_NVS_ENCRYPTION=y`, generate `mfg_nvs.bin` in **encrypted mode** using `sample_encryption_keys.bin`.
2. Register `sample_encryption_keys.bin` as a flash target for the `nvs_key` partition.

## Flash

**First flash** (eFuse does not yet contain the encryption key):

```bash
./build.py flash -p /dev/ttyUSBx
```

Use the regular `flash` command for the first flash. The bootloader will automatically generate the encryption key and encrypt flash on the first boot.

**Subsequent reflash** (eFuse already contains the encryption key):

```bash
esptool.py --port /dev/ttyUSBx erase_flash
./build.py encrypted-flash -p /dev/ttyUSBx -b 115200 monitor
```

The `encrypted-flash` command uses the existing eFuse key to perform encrypted flashing for partitions marked `encrypted`. `at_customize.bin` and `mfg_nvs.bin` are flashed as plaintext (`ALWAYS_PLAINTEXT`) because:
- `mfg_nvs.bin` is already encrypted at build time by the NVS partition generator; it does not need Flash-layer encryption.
- `at_customize.bin` is a metadata table that contains no sensitive data and does not require Flash-layer encryption.

## First Boot

On the first boot with a blank flash:
1. The bootloader generates the Flash Encryption key and writes it to eFuse.
2. The bootloader encrypts all partitions marked `encrypted` in place.
3. The application reads the NVS encryption key from the `nvs_key` partition to decrypt `mfg_nvs`.

You should see log output similar to:

```
I (xxx) flash_encrypt: Flash encryption mode is DEVELOPMENT
I (xxx) at-init: NVS encryption enabled, mfg_nvs is encrypted successfully
I (xxx) at-init: at param mode: 1
```

`at param mode: 1` indicates that `mfg_nvs` was successfully initialized under NVS Encryption.

## Development Mode Limitations

- The Flash Encryption key is stored in eFuse. In Development Mode, the number of times encrypted data can be reflashed is limited (controlled by the `SPI_BOOT_CRYPT_CNT` eFuse).
- To start over, you can flip the `SPI_BOOT_CRYPT_CNT` bits using `espefuse.py burn_efuse`, or use a different chip.
